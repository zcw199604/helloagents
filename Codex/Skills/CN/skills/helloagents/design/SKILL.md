# 方案设计 - 详细规则

**目标:** 构思可行方案并制定详细执行计划，生成 `helloagents/<branch-name>/plan/` 目录下的方案包

**前置条件:** 需求分析已完成（评分≥7分）

**重要:** 方案设计必须创建新方案包，适用于所有模式（交互确认/全授权/规划命令）

**执行流程:**
```
方案构思 → [用户确认/交互式规划用户选择/推进模式下连续] → 详细规划（创建新方案包）
```

---

## 方案构思

### 动作步骤

**1. 检查知识库状态并处理**
- 按 G10 快速决策树判定
- 如需创建/重建知识库 → 读取 `kb` Skill执行完整流程

**2. 读取知识库**
- 按 G10 快速流程执行（先检查知识库 → 不足则扫描代码库）
- 如需详细规则 → 读取 `kb` Skill

**3. 判定项目规模**
- 按 G4 规则执行

**4. 判定需求类型并选择模板**
- 按G8判定是否触发产品设计原则
- 技术变更（未触发G8）: 使用基础模板
- 产品功能（触发G8）: 使用完整模板（包含产品分析章节）

**5. 产品视角分析（步骤4判定为"产品功能"时执行）**
- 用户画像、场景分析、痛点分析
- 价值主张、成功指标
- 人文关怀考量

**6. 任务复杂度判定**

满足任一条件为复杂任务:
```yaml
- 需求属于"新项目初始化"或"重大功能重构"
- 涉及架构决策
- 涉及技术选型
- 存在多种实现路径
- 涉及多个模块(>1)或影响文件数>3
- 用户明确要求多方案
```

**6.5 大范围方案拆分**

```yaml
触发条件: 需求分析标记为大范围需求，或方案构思时发现无法在单个可验证闭环内完成
拆分原则:
  - 按业务能力、模块边界、风险等级或可交付闭环拆分
  - 每个切片必须可独立验证、可独立回滚、可独立记录知识库
  - 当前方案包只覆盖一个切片，禁止把多个弱相关切片塞进同一任务清单
  - 未选切片写入 why.md 的"范围外"或"后续计划"，不得写入本次 task.md
交互确认模式或 MODE_PLANNING_INTERACTIVE=true: 如当前切片未明确，输出方案构思选择，让用户选择先执行哪一片
推进模式（不含交互式规划）: 选择风险最低、改动最小且价值闭环清晰的切片，并在方案包中记录假设
```

**7. 方案构思**

<solution_design>
**方案评估标准:**
- 优点
- 缺点
- 性能影响
- 可维护性
- 实现复杂度
- 风险评估（含EHRB）
- 成本估算
- 是否符合最佳实践
- 大型项目最小改动: 优先局部修复、兼容适配和渐进式演进；完整重构必须有明确必要性和风险缓解

**方案构思推理过程（在 <thinking> 标签中完成，不输出给用户）：**

```
<thinking>
1. 列举所有可能的技术路径
2. 逐一评估每个路径的优缺点、风险、成本
3. 筛选出 2-3 个最可行的方案
4. 确定推荐方案及理由
</thinking>
```

**基于推理结果执行：**

**复杂任务（强制方案对比）:**
- 生成 2-3 个可行方案
- 详细评估每个方案
- 确定推荐方案和理由
- 输出格式: 推荐方案标题后加"推荐"标识
  - 例: "方案1（最小变更修复-推荐）" vs "方案2（完整重构）"
- 交互确认模式或 MODE_PLANNING_INTERACTIVE=true: 输出方案对比，询问用户选择
- 推进模式（不含交互式规划）: 选择推荐方案（不输出对比）

**简单任务:**
- 直接确定唯一可行方案
- 简要说明方案
</solution_design>

### 方案构思 输出格式（等待用户选择方案时）

行首: `❓【HelloAGENTS】- 方案构思`

**输出内容(≤5条要点):**
```
❓【HelloAGENTS】- 方案构思

- 📚 上下文: [项目规模] | [知识库状态]
- 📋 需求类型: [技术变更/产品功能]
- 🔍 复杂度: [复杂任务] - [判定依据]
- 💡 方案对比:
  - 方案1: [名称-推荐] - [一句话说明]
  - 方案2: [名称] - [一句话说明]
- ⚠️ 风险提示: [如有EHRB或重大风险]

────
🔄 下一步: 请输入方案序号(1/2/3)选择方案
```

**详细方案说明:** 如用户需要详细对比，可追问后展开

### 方案构思 子阶段转换

```yaml
复杂任务:
  交互确认模式或 MODE_PLANNING_INTERACTIVE=true:
    - 用户选择有效序号(1-N) → 进入详细规划
    - 用户拒绝所有方案 → 输出重新构思询问格式
      - 确认重新构思: 返回方案构思，重新构思
      - 拒绝: 提示"已取消方案设计"，流程终止
      - 其他输入: 再次询问
  推进模式（不含交互式规划）:
    - 选择推荐方案 → 立即静默进入详细规划

简单任务: 直接进入详细规划
```

**重新构思方案询问格式:**
```
❓【HelloAGENTS】- 方案确认

所有方案均被拒绝。

[1] 重新构思 - 基于反馈重新设计方案
[2] 取消 - 终止方案设计

────
🔄 下一步: 请输入序号选择
```

## 详细规划

**前提:** 用户已选择/确认方案（来自方案构思）

**重要:** 必须创建新方案包，使用当前时间戳，不得复用 `helloagents/<branch-name>/plan/` 中的遗留方案

### 动作步骤

**所有文件操作遵循G5静默执行规范**

**1. 创建新方案包目录**

```yaml
路径: helloagents/<branch-name>/plan/YYYYMMDDHHMM_<feature>/
冲突处理:
  1. 检查 helloagents/<branch-name>/plan/YYYYMMDDHHMM_<feature>/ 是否存在
  2. 如不存在 → 直接创建
  3. 如存在 → 使用版本后缀: helloagents/<branch-name>/plan/YYYYMMDDHHMM_<feature>_v2/
     (如 _v2 也存在，则递增为 _v3, _v4...)
示例:
  - 首次创建: helloagents/<branch-name>/plan/202511181430_login/
  - 同名冲突: helloagents/<branch-name>/plan/202511181430_login_v2/
```

**2. 新库/框架文档查询（如需要）**
```yaml
触发条件: 方案涉及项目中从未使用过的第三方库/框架，或涉及重大版本升级
执行方式: 使用联网搜索或MCP工具(Context7)查询最新文档
记录位置: how.md 的 技术方案 章节
```

**3. 生成方案文件**

读取 `templates` Skill 获取模板，生成:
- `why.md` (变更提案/产品提案)
- `how.md` (技术设计+ADR)
- `task.md` (任务清单)

**任务清单编写规则:**
```yaml
单任务代码改动量控制:
  - 常规项目: ≤3文件/任务
  - 大型项目: ≤2文件/任务
大型项目最小改动:
  - 任务必须优先限定在直接相关模块和最小文件集合
  - 禁止把风格整理、目录搬迁、依赖升级、公共接口重命名混入功能实现
  - 如确需重构，必须拆为独立任务并说明必要性、回滚方式和验证命令
设计边界:
  - 在 how.md 明确范围内/范围外、模块职责、接口契约、数据边界和依赖边界
  - task.md 中每个代码任务必须标明目标文件、验证场景和依赖关系
验证任务: 定期插入
安全检查: 必须包含安全检查任务
TDD任务: 对强制/建议启用TDD的可测试行为，读取 `tdd` Skill，将任务拆为 RED → GREEN → REFACTOR → VERIFY
TDD例外: 例外任务必须标注 TDD-EXEMPT 和原因
并行子代理标注:
  - 当存在可并行任务组时，读取 `hello-subagent` Skill 的触发条件
  - 在 task.md 中标注可并行组、允许写入范围、冲突域和验证命令
  - 若文件边界或依赖关系不清晰，不标注为可并行
```

**4. 风险规避措施制定**
- 基于方案构思风险评估，按G9制定详细规避措施
- 交互确认模式或 MODE_PLANNING_INTERACTIVE=true: 询问用户
- MODE_FULL_AUTH=true 或 (MODE_PLANNING=true 且 MODE_PLANNING_INTERACTIVE=false): 规避风险
- 写入 `how.md` 的 安全与性能 章节

**4.5 方案自审门禁**

<design_self_review_gate>
**执行时机:** `why.md`、`how.md`、`task.md` 初稿生成后，输出阶段总结前

**自审清单（必须全部通过）:**
- 范围一致: `why.md` 的需求、`how.md` 的技术方案、`task.md` 的任务清单覆盖同一需求切片
- 边界清晰: 范围内/范围外、模块职责、接口契约、数据边界、依赖边界无歧义
- 最小改动: 大型项目方案优先局部修改；不存在无必要的重构、迁移、依赖升级或公共API改名
- 可验证: 每个核心场景都有对应任务和验证方式；TDD适用性已处理
- 风险闭环: EHRB、安全、性能、回滚和兼容性风险已有缓解措施
- 无占位遗留: 不保留未解释的 TODO/TBD/待定/???，不留下互相矛盾的描述

**失败处理:** 静默修正方案包后重新自审；若无法消除关键不确定性，按G3输出不确定因素并等待用户选择
</design_self_review_gate>

**5. 设置方案包跟踪变量**
```yaml
设置: CREATED_PACKAGE = 步骤1创建的方案包路径
用途: 在全授权命令中传递给开发实施，确保执行正确的方案包
```

**6. 多模型审查询问（可选）**

```yaml
触发时机: 方案包文件创建完成后、输出阶段总结前
适用模式: 交互确认模式 / 规划命令

全授权命令处理:
  - 跳过询问，直接进入开发实施
  - 在最终总结末尾追加提示: "💡 多模型审查: 如需审查方案包，可在规划命令完成后单独触发"
```

⚠️ **CRITICAL - 强制要求:**
- ALWAYS使用G6.1统一输出格式
- NEVER使用自由文本替代规范格式
- 输出前MUST验证格式完整性

严格调用 G6.1 统一输出格式，填充以下数据：

1. **阶段名称:** `方案设计`
2. **阶段具体内容(≤5条要点):**
   - 📚 知识库状态
   - 📝 方案概要（复杂度、方案说明）
   - 📋 变更清单
   - 📊 任务清单概要
   - ⚠️ 风险评估（如检测到EHRB）
3. **文件变更清单:**
   - `helloagents/<branch-name>/plan/YYYYMMDDHHMM_<feature>/why.md`
   - `helloagents/<branch-name>/plan/YYYYMMDDHHMM_<feature>/how.md`
   - `helloagents/<branch-name>/plan/YYYYMMDDHHMM_<feature>/task.md`
4. **下一步建议:**
   - 交互确认模式/规划命令: 输出多模型审查询问（见"多模型审查询问格式"）
   - 全授权命令: 直接进入开发实施，总结末尾追加多模型审查提示
5. **遗留方案提醒:**
   - 按G11扫描 `helloagents/<branch-name>/plan/` 目录
   - 如检测到遗留方案包（排除本次创建的方案包），按G11规则显示

## 阶段转换规则

```yaml
交互确认模式 / 规划命令:
  - 输出阶段总结
  - 输出"多模型审查询问格式"，等待用户选择
  - 用户选择 [1] 启动多模型审查:
      - 读取 `multi_model` Skill，按 DESIGN 阶段协作规则执行
      - 输出审查结论（共识项、分歧项、最终建议）
      - 审查完成后进入后续阶段转换逻辑
  - 用户选择 [2] 跳过:
      - 进入后续阶段转换逻辑
  - 后续阶段转换逻辑:
      - 交互确认模式: 询问"是否进入开发实施?(是/否)"，等待确认
        - 明确确认 → 进入开发实施
        - 明确拒绝 → 流程终止
        - Feedback-Delta → 按Feedback-Delta规则处理
        - 其他输入 → 视为新的用户需求，按路由机制重新判定
      - 规划命令: 输出整体总结 → 停止 → 清除MODE_PLANNING/MODE_PLANNING_INTERACTIVE

推进模式:
  - 全授权命令: 完成方案设计 → 跳过多模型审查询问 → 立即静默进入开发实施
                总结末尾追加: "💡 多模型审查: 如需审查方案包，可在规划命令完成后单独触发"

关键约束（只有以下3种情况可以进入开发实施）：
  1. 方案设计完成后用户明确确认（含多模型审查后确认）
  2. 全授权命令(~auto等)触发且已完成方案设计
  3. 执行命令(~exec等)触发且 `helloagents/<branch-name>/plan/` 中存在方案包
```
