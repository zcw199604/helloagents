# 开发实施入口与执行步骤

## 强制前置检查

<develop_entry_gate>
**说明：** 即使路由判定进入开发实施，此检查仍会验证合法性（双重保险）

**开发实施的合法条件（满足任一即可）：**

```yaml
条件A - 方案设计完成后确认:
  验证方法: 当前会话存在刚创建且完整的方案包(CREATED_PACKAGE或等价状态) 且 当前用户输入为明确确认
  说明: 允许方案设计完成后经过多模型审查、跳过审查提示或"是否进入开发实施"确认提示

条件B - 全授权命令:
  验证方法: MODE_FULL_AUTH=true 且 AUTH_WORKFLOW_ID=WORKFLOW_ID

条件C - 执行命令:
  验证方法: MODE_EXECUTION=true 且 AUTH_WORKFLOW_ID=WORKFLOW_ID

条件D - 系统化调试只读入口:
  验证方法: 路由命中系统化调试模式，且用户只要求诊断或当前写入授权/证据不足
  权限: 仅允许执行步骤4.6的根因调查、复现、最小验证和风险判断

条件E - 用户明确授权的自适应开发:
  验证方法: 用户明确要求修复/修改/实现；风险等级=低或中；EHRB=无；无破坏性公共契约或真实数据迁移
  权限: 在用户请求范围内修改代码、测试和必要文档；不要求先创建方案包或使用特殊命令
  升级: 根因或范围升级为高风险时立即停止写入，转入方案设计和确认
```

**验证失败处理：**
```
IF 不满足任何条件:
  输出: "❌ 路由错误: 进入开发实施需满足前置条件。当前条件不满足，已重新路由。"
  执行: 将当前用户消息按路由优先级重新判定
  终止: 在 finally 执行 RESET_WORKFLOW_STATE，结束开发实施流程
```
</develop_entry_gate>

## 执行步骤

**重要:** 使用宿主精确编辑工具并保留已有改动；只简要报告关键进展，不逐文件输出模板。

### 系统化调试只读入口旁路

```yaml
IF 满足条件D - 系统化调试只读入口:
  - 跳过步骤1、步骤4中对 CURRENT_PACKAGE 和方案包文件的强制要求
  - 可按需执行步骤2、步骤3获取知识库和项目上下文
  - 直接进入步骤4.6，仅允许只读根因调查、复现、最小验证和方案判断
  - 不设置 CURRENT_PACKAGE，不更新 task.md，不写入 qa-review.json，不同步 CHANGELOG，不迁移 history/
  - 根因明确且需要修改时，重新核对条件A/B/C/E；未获授权的改动保持只读，高风险先设计和确认
  - 根因明确且用户原请求已授权低/中风险修复时，可重新校验条件E后进入自适应开发
  - 根因明确但无需修改代码或文档时，保存调查结论，执行 RESET_WORKFLOW_STATE 后输出并停止
```

### 自适应开发无方案包旁路

```yaml
IF 满足条件E 且本次不需要方案包:
  - 锁定用户请求、范围边界、成功标准和验证方式
  - 不扫描或消费 `plan/` 中的遗留方案包，不设置 CURRENT_PACKAGE
  - 步骤4读取方案包、步骤7.6归档目标、步骤12迁移按“不适用”跳过
  - 步骤7.5默认不写 qa-review.json，改在最终摘要记录实际验证命令、结果和剩余风险；用户明确要求结构化 QA 时按该 skill 的独立输出规则保存
  - 知识库只在稳定项目知识、公共行为或技术约定变化时同步；CHANGELOG 只记录发布相关变化
  - 其余根因调查、TDD、安全检查、测试和一致性核对不得跳过
```

### 步骤1: 确定待执行方案包

```yaml
全授权命令(MODE_FULL_AUTH=true):
  - 读取CREATED_PACKAGE变量（方案设计阶段设置的方案包路径）
  - 检查该方案包是否存在且完整
    - 存在且完整 → 使用该方案包，设置CURRENT_PACKAGE = CREATED_PACKAGE
    - 不存在或不完整 → 按 output-format Skill 的 G6.2 错误格式输出并停止
  - 忽略 `helloagents/<branch-name>/plan/` 中的其他遗留方案包

自适应开发(条件E):
  - 默认不要求方案包；记录本轮范围、成功标准和验证方式后继续
  - 用户明确指定方案包时按该方案包执行，不从 `plan/` 自动选择其他遗留项
  - 多步骤、跨模块或需要恢复执行时，可创建合法轻量方案包并设置 CURRENT_PACKAGE

交互确认模式/执行命令(MODE_EXECUTION=true):
  - 扫描 `helloagents/<branch-name>/plan/` 目录下所有方案包
  - 不存在方案包 → 按 output-format Skill 的 G6.2 错误格式输出并停止
  - 方案包完整性: `why.md`+`how.md`+`task.md` 齐全，或 `task.md` 顶部标注 `模式: 轻量迭代` 的简化方案包（仅 task.md，按完整处理；执行时跳过 why.md/how.md 读取）
  - 方案包不完整 → 按 output-format Skill 的 G6.2 错误格式输出并停止
  - 单个完整方案包 → 设置CURRENT_PACKAGE，继续执行
  - 多个方案包 → 列出清单，等待用户选择
    - 输出前设置 PENDING_INTERACTION=PACKAGE_CHOICE
    - 用户输入有效序号(1-N) → 设置CURRENT_PACKAGE，继续执行
    - 用户输入取消/拒绝 → 执行 RESET_WORKFLOW_STATE，按 output-format Skill 的 G6.2 取消格式输出，流程终止
    - 无效输入 → 再次询问

异常输出示例:
  方案包不存在:
    ```
    ❌【HelloAGENTS】- 执行错误

    错误: 未找到可执行的方案包
    - 原因: `helloagents/<branch-name>/plan/` 目录为空或不存在

    ────
    🔄 下一步: 请先使用 ~plan 命令创建方案，或进入方案设计阶段
    ```

  方案包不完整:
    ```
    ❌【HelloAGENTS】- 执行错误

    错误: 方案包不完整
    - 方案包: [方案包名称]
    - 缺失文件: [why.md/how.md/task.md]

    ────
    🔄 下一步: 请补充缺失文件或重新创建方案包
    ```
```

### 步骤2: 检查知识库状态并处理

执行方式:
- 只检查当前范围的相关知识；缺失处理见 [kb](../../kb/SKILL.md)
- 实际需要创建或更新时先通过 `kb` 的写入收益门禁，不自动重建
- 自适应低/中风险路径只检查相关知识是否存在，不因知识库缺失而创建整套知识库或阻断实现

### 步骤3: 读取知识库并获取项目上下文

执行方式:
- 优先复用相关知识和有效分析，不足则定向搜索代码与测试
- 如需详细规则 → 读取 `kb` Skill
- 自适应路径只读取与当前范围直接相关的代码和文档

### 步骤4: 读取当前方案包

先读取 `task.md` 并判定方案包类型:

- 完整方案包: 继续读取 `why.md` 和 `how.md`。
- 轻量方案包: 读取 `task.md` 的“轻量方案包元数据”，校验范围摘要、核心场景、知识库同步、ADR 和验证策略齐全；不得再要求 `why.md/how.md`。
- 自适应无方案包: 使用步骤1锁定的用户请求、范围、成功标准和验证方式，不读取或创建方案包。

读取目的:
- `why.md`: 确认需求、范围、核心场景和风险。
- `how.md`: 确认技术方案、ADR、接口/数据/依赖边界、测试与部署约束。
- `task.md`: 确认执行任务、依赖顺序和验证命令。

### 步骤4.5: 并行子代理适配判断（可选）

当 `task.md` 中存在多个独立、边界清晰、可验证且无文件写入重叠的任务组时，读取 `hello-subagent` Skill，按其规则进行子任务派发、上下文裁剪、冲突控制和结果验收。

不满足子代理触发条件时，由主代理按后续步骤顺序执行任务。

### 步骤4.6: 系统化调试门禁（适用时）

<systematic_debugging_gate>
**触发条件（满足任一）:**
```yaml
- 用户报告 Bug、测试失败、构建失败、运行异常、性能回退、flaky/超时、回归问题
- task.md 中任务类型为缺陷修复、失败测试修复、构建修复、稳定性修复
- 开发实施过程中出现新的阻断性测试失败或复现异常
```

**根因调查要求（修复前必须完成）:**
- 读取完整错误、日志、stack trace、失败测试名和触发命令，禁止只看最后一行错误
- 稳定复现问题；如无法复现，记录环境、步骤、输入、频率和已排除因素
- 检查近期变更、依赖/配置/环境差异，定位失败是输入、状态、边界条件、并发时序、集成契约还是环境问题
- 多组件链路（如 CI→构建→签名、API→服务→数据库、前端→网关→后端）必须在每个边界记录输入、输出、环境/配置传播和责任层，先证明问题在哪一层产生
- 从报错点沿调用链/数据流向上追踪坏数据或坏状态的来源，优先从源头修复，禁止只在深层报错点做症状补丁
- 测试单跑通过但整套失败，或发现脏文件、数据库记录、缓存、全局变量、时间/随机种子污染时，必须定位污染源测试；优先用二分、最小测试组合或顺序复现找 polluter，禁止只在失败测试里清理结果
- 每轮只提出一个根因假设，并用最小验证手段确认或否定；验证失败后回到调查，不叠加猜测性补丁
- 异步或 flaky 问题优先等待真实条件（状态、事件、DOM、端口、文件、队列为空等），禁止用固定 sleep 猜时间；只有验证真实时间语义时才允许固定等待并记录原因
- 允许临时诊断日志/断言，但必须在提交最终实现前删除或转为项目认可的可观测性代码

**根因确认后的修复规则:**
- 坏数据/坏状态类问题必须优先修复源头，并按需要补入口校验、业务不变量、边界兼容和诊断观测防线
- 防线只覆盖本次根因和可绕过路径，仍遵守大型项目最小改动约束，禁止扩成全面重构
- 满足条件E的普通缺陷直接补回归测试、实施最小修复并验证，不要求创建方案包或二次确认
- 只读诊断只有在用户随后明确授权且重新校验为低/中风险后才能进入修改
- 时间压力、权威压力、连续失败后的沉没成本都不能跳过根因调查；证据不足时暂停猜测性修改，继续必要调查或说明阻塞性缺口

**停止扩大规则:**
- 连续3次修复尝试失败、根因仍不明确、或修复需要扩大到架构/公共契约时，停止继续改代码
- 说明不确定因素并重新评估范围，必要时进入方案设计，不允许继续盲目重构
</systematic_debugging_gate>

### 步骤5: 按任务清单执行代码改动

```yaml
执行规则:
  - 有方案包时严格按 task.md 逐项执行；自适应无方案包时严格按步骤1锁定的范围和成功标准执行
  - 如触发系统化调试门禁，先完成根因调查和单假设验证，再修改生产代码
  - 如启用并行子代理，必须由主代理先按 hello-subagent Skill 完成派发前检查、文件边界声明和返回格式约束
  - 子代理结果只作为中间材料，主代理必须复核 changed_files、验证结果和 task.md 状态后再进入后续质量检查
  - 如任务命中TDD适用性（新功能、Bug修复、行为变更、核心逻辑调整或测试策略设计），先读取 `tdd` Skill
  - 默认先完成对应RED任务，再修改生产代码
  - 受遗留代码、无测试框架、环境不可复现或用户约束限制时，必须记录约束、替代验证方式和 TDD-EXEMPT 原因，再按既有验证策略执行

任务成功处理:
  - 有方案包时，每个任务执行成功后立即将状态从 [ ] 更新为 [√]
  - 无方案包时，在最终摘要中逐项核对成功标准，不创建虚拟任务状态

任务跳过处理(状态更新为 [-]):
  - 任务依赖的前置任务失败
  - 任务条件不满足
  - 任务已被其他任务的实现覆盖
  - 仅适用于存在 task.md 的路径

任务失败处理(状态更新为 [X]):
  - 记录错误信息（用于迁移前添加备注）
  - 只继续执行不依赖失败项且不会扩大损害的任务
  - 如失败导致成功标准、核心验证、安全或必要知识同步不可满足，所有模式立即停止归档；在已有授权内修复并验证，无法安全继续时设置 `PENDING_INTERACTION=TEST_FAILURE_DECISION`
  - 用户明确选择承担非阻断风险后才可继续；全授权命令不得自动把失败任务迁移为成功完成
  - 无方案包时不写任务状态，但同样按阻断级别停止、修复或报告

代码编辑技巧:
  - 大文件处理(≥2000行): 搜索定位 → 分段读取 → 使用宿主平台的精确补丁工具修改
  - 每次补丁只修改一个逻辑单元
```

### 步骤5.4: 最小充分实现约束

<minimal_sufficient_implementation>
**适用条件:** 所有代码改动。

**执行约束:**
- 只实现当前成功标准、已确认风险和受影响契约所需的最小逻辑，不为假设性未来需求增加抽象层、配置项、兼容分支、重试、回退或兜底。
- 防御性校验、错误处理和观测能力必须对应真实输入边界、已知故障模式、安全要求或既有项目约定；优先复用现有错误上下文、日志和追踪机制，不默认增加全量埋点。
- 验证目标是保护核心路径并让未直接覆盖的故障可定位，不要求在测试阶段穷尽全部潜在问题。
- 若规模、复杂度、故障成本或公共契约影响证明需要更完整的防线与验证，可扩大范围，但必须记录依据并保持实现与验证成本相称。
</minimal_sufficient_implementation>

### 步骤5.5: 大型项目最小改动执行约束

<large_project_minimal_change>
**触发条件:** 项目规模判定为大型项目，或任务影响公共模块/跨模块契约

**执行约束:**
- 优先做满足当前方案包成功标准的最小代码改动，避免顺手重构
- 默认不做目录搬迁、批量重命名、公共API改签名、依赖升级、格式化全文件等非必要改动
- 优先保持现有架构、命名、错误处理、日志、测试风格和兼容行为
- 如发现需要大范围重构才能继续，停止扩大改动，说明影响和取舍并按 [路由规则](../../routing/SKILL.md) 判断授权
- 修复缺陷时优先定位根因和最小补丁，避免用整体重写掩盖问题
- 验证范围应覆盖本次触达路径和受影响契约，不因改动小而跳过测试/审计
- 大型或复杂项目可按故障成本和影响面扩大测试、审查与防御边界；有明确风险依据的全面验证不视为过度工程化
</large_project_minimal_change>

### 步骤6: 代码安全检查

检查内容:
- 不安全模式（eval、exec、SQL拼接等）
- 敏感信息硬编码
- EHRB风险规避

### 步骤7: 质量检查与测试

```yaml
测试执行: 运行task.md中定义的测试任务、自适应路径锁定的验证命令，或项目已有相关测试套件

TDD门禁（适用时严格执行）:
  - RED: 测试必须先失败，且失败原因匹配目标行为
  - GREEN: 仅做最小实现让相关测试通过
  - REFACTOR: 仅在测试通过后重构，重构后必须复测
  - 反模式检查: 不测试mock自身行为、不添加test-only生产接口、复杂mock优先转fake/真实组件/集成测试

测试失败处理规则（严格执行）:
  预期 RED: 失败原因与待实现行为匹配时，按 TDD 继续 GREEN，不作为交付失败或请求重复授权
  ⛔ 阻断性测试（核心功能）:
    - 失败阻止归档和成功总结，禁止自动跳过；所有模式保持同一门禁
    - 修复在既有低/中风险授权内时，回到根因调查并修复、重测，无需重复询问
    - 缺少必要输入、超出授权或无法安全继续时，设置 PENDING_INTERACTION=TEST_FAILURE_DECISION 并说明具体原因，等待修复所需决定或终止

  ⚠️ 警告性测试（重要功能）:
    - 作为 P1 记录到方案包 QA findings 或无方案包摘要，默认阻止归档
    - 先在已有授权内修复并验证；仍有剩余风险时，只有用户通过 QA_RISK_DECISION 明确接受后才能交付

  ℹ️ 信息性测试（次要功能）:
    - 失败时在总结中记录
    - 继续执行后续步骤
```

### 步骤7.5: QA 证据记录

有方案包或用户要求结构化审计时，读取 `qa-review` Skill 形成交付前 QA 证据；自适应无方案包路径保留等价的最终验证摘要。

执行要求:
- 完整方案包对照 `why.md/how.md/task.md`；轻量方案包对照 `task.md` 的轻量方案包元数据和完成标准。
- 记录实际运行的验证命令、结果摘要、未运行原因和替代验证。
- 写入 QA 文件时，TDD 证据使用 schema v3 `qa-review.json.tdd`，记录适用性、决策、目标行为和实际阶段结果；豁免记录原因和替代验证，证据复用按 `verification-before-completion` 判断。
- 对阻断项、警告项、信息项分级；阻断项必须写明文件定位和修复方向。
- 有方案包时在当前方案包目录写入 `qa-review.json`，确保步骤12迁移时证据一并进入 history；用户单独要求结构化 QA 时按 `qa-review` 的输出位置规则处理。
- 自适应无方案包且用户未要求结构化 QA 时不创建孤立的 `qa-review.json`；最终总结记录实际命令、结果、TDD/豁免依据和剩余风险。
- 证据记录后执行本地 QA 门禁: P0 阻止归档且不可接受风险；P1 默认阻止归档，按 `qa-review` 先修复，需接受剩余风险时设置 `PENDING_INTERACTION=QA_RISK_DECISION`；仅 P2、已解决项或用户明确接受的 P1 可交付。
- 全授权命令和执行命令不得绕过本地 QA 门禁；遇到 P0/P1 先在已有授权内修复并重测，需要额外决定或接受 P1 风险时才按相应等待态处理。

### 步骤10: 一致性审计

<consistency_audit>
**审计时机:** 开发实施阶段完成知识库操作后立即执行

**审计内容:**
1. **完整性:** 本次修改、测试和必要文档覆盖已锁定的成功标准。
2. **一致性:** 本次触达的 API/数据模型/稳定约定与代码一致，无新增死链或矛盾。

**真实性优先级（冲突解决机制）:**
```
1. 代码是执行真实性的唯一来源 (Ground Truth)
   → 运行时行为、API签名、数据结构以代码为准

2. 默认修正方向: 修正知识库以符合代码
   → 发现不一致时，必须更新文档以反映代码的客观事实

3. 例外（修正代码）:
   - 知识库内容来自当前会话最近的方案设计/开发实施方案包（刚设计好的方案）
   - 代码有明显错误（Bug）
   - 错误信息指向代码问题

4. 存疑时: 双向验证，优先信任最近的代码变更
```
</consistency_audit>
