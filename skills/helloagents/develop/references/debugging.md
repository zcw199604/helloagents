# 系统化调试

本文件是调试规则的唯一定义。

## 触发

- 用户报告 Bug、测试/构建失败、运行异常、性能回退、flaky/超时、错误日志或回归问题。
- 方案包任务类型为缺陷、失败测试、构建或稳定性修复。
- 实施过程中出现新的阻断性失败。

## 根因调查

修改生产代码前完成:

- 读取完整错误、日志、stack trace、失败测试名和触发命令，不只看最后一行。
- 稳定复现；无法复现时记录环境、步骤、输入、频率和已排除因素。
- 检查近期变更以及依赖、配置和环境差异，判断问题属于输入、状态、边界条件、并发时序、集成契约还是环境。
- 多组件链路在每个边界核对输入、输出和配置传播，先证明问题产生在哪一层。
- 从报错点沿调用链或数据流向上追踪坏数据、坏状态的来源，从源头修复，不在深层报错点打症状补丁。
- 测试单跑通过但整套失败，或发现残留文件、数据库记录、缓存、全局变量、时间/随机种子污染时，用二分或最小测试组合定位 polluter，不只在失败测试里清理结果。
- 每轮只提出一个可证伪的根因假设，用最小手段验证；验证失败回到调查，不叠加猜测性补丁。
- 异步或 flaky 问题等待真实条件（状态、事件、端口、文件、队列为空等），不用固定 sleep 猜时间；只有验证真实时间语义时才固定等待并记录原因。
- 临时诊断日志和断言在交付前删除，或转为项目认可的可观测性代码。

时间压力和连续失败的沉没成本都不能跳过根因调查。

## 出口

- **直接修复:** 根因确认，且满足 `develop` 入口的任一写入条件。先补能复现问题的回归测试，再做最小修复并验证；防线只覆盖本次根因和可绕过路径。不要求方案包或再次确认。
- **只读诊断:** 用户只要求定位或解释，或证据不足以安全修改。报告根因、证据和不确定因素；需要环境、日志或复现条件时向用户说明。
- **升级:** 连续 3 次修复尝试失败、根因仍不明确，或修复需要架构变更、破坏性公共契约、真实数据迁移、生产操作等高风险动作时，停止改代码，说明不确定因素，转入 `design` 并在写入前确认。
