# 测试驱动开发质量规则

## 目标

在不改变 HelloAGENTS 三阶段主流程的前提下，将测试驱动开发作为横切质量规则嵌入需求分析、方案设计和开发实施。

## 适用性判定

```yaml
强制启用:
  - 新功能或可观察行为变更
  - Bug修复且存在可复现条件
  - 核心业务逻辑调整
  - 公共API/公共方法新增或语义变更
  - 历史缺陷回归测试补齐

建议启用:
  - 重构但可通过现有测试保护
  - 边界条件、错误处理、兼容性逻辑调整
  - 用户未明确要求测试但存在自动化验证入口

例外:
  - 纯文档、知识库、注释、格式化
  - 无行为变化的重命名或机械迁移
  - 探索性spike或一次性诊断
  - 当前项目无测试框架且本次不适合引入
  - 用户明确要求只做非生产代码或只读分析

不确定:
  - 默认按“建议启用”处理，在方案包中加入测试任务或记录例外原因
```

## 三阶段接入

### 需求分析
- 标记 `TDD适用性: 强制 | 建议 | 例外 | 不确定`。
- 提取可观察行为、失败复现条件、边界场景和验收命令。
- 缺少可测试成功标准时，作为需求完整性扣分项或追问点。

### 方案设计
- 对每个可测试行为生成 `RED → GREEN → REFACTOR → VERIFY` 任务序列。
- 例外任务必须写明 `TDD-EXEMPT` 和原因。
- 测试任务必须排在生产实现任务之前。

### 开发实施
- 修改生产代码前，先完成对应 RED 任务并确认失败原因匹配目标行为。
- GREEN 阶段只做最小实现，禁止顺手重构或扩大范围。
- REFACTOR 只能在相关测试通过后执行，重构后必须复测。
- RED/GREEN/REFACTOR 证据可静默记录到任务备注；开发实施步骤7.5必须将最终证据写入 schema v3 `qa-review.json.tdd`，不破坏推进模式静默规则。

## 结构化证据

- 新生成的 QA 记录使用 schema v3，`tdd.classification` 标记 `mandatory`、`recommended`、`exempt` 或 `uncertain`，并记录最小目标行为集合。
- `tdd.decision=tdd` 时，`red.result` 必须为 `failed`，`green`、`refactor` 与 `verify` 的结果必须为 `passed`；即使无需改动也要将 `refactor.performed=false` 与复测命令写入。
- `tdd.decision=exempt` 时，必须写入 `exempt_reason` 与 `alternative_verification`。强制适用任务不得直接豁免，应先把适用性重新判定为例外并说明环境或用户约束。
- 对生产实现早于本次测试的表征测试，可使用 `TDD-EXEMPT`，但理由必须明确说明无法构造真实 RED，不得把直接通过的测试伪装为 RED。

## RED-GREEN-REFACTOR 规则

```yaml
RED:
  - 先写测试，再改生产代码
  - 测试必须失败
  - 失败原因必须对应目标行为，而非语法错误、环境错误或断言写错

GREEN:
  - 写最小生产实现让测试通过
  - 禁止引入无关重构
  - 禁止扩大任务范围

REFACTOR:
  - 只在测试通过后整理实现
  - 保持行为不变
  - 重构后重新运行相关测试

VERIFY:
  - 优先运行相关最小测试
  - 条件允许时运行项目既有更广测试套件
  - 失败按 develop Skill 的阻断/警告/信息规则处理
```

## 测试设计与覆盖策略

### 覆盖目标
- 测试采用风险驱动的最小充分覆盖，不以穷尽全部输入、分支或潜在问题为目标，也不以覆盖率数字替代行为验证。
- 优先保护新增可观察行为、核心业务路径、受影响契约、高风险边界和历史回归；低风险且未触达的外围路径不机械扩展测试。
- 对已识别但未直接覆盖的高/中风险路径，应记录取舍、替代验证和剩余风险；优先复用项目既有错误上下文、日志和观测能力支持生产问题溯源，不为假设性故障堆叠防御代码或全量埋点。
- 大型、复杂或高故障成本项目可以基于风险扩大测试层级、覆盖范围和验证深度；有明确风险依据的全面验证不视为过度工程化。

### 覆盖层级
- 优先为新增可观察行为补充单元测试；跨模块协作、持久化、网络边界或关键流程补充集成测试。
- 端到端测试只覆盖核心用户路径和高风险回归，避免用 E2E 替代低层测试。
- Bug修复必须优先写能复现缺陷的失败测试，再实施修复。
- 对无法自动化验证的场景，必须记录手工验证步骤或 TDD-EXEMPT 原因。

### 用例选择
- 根据目标行为和风险，从正常路径、错误路径、边界值、空值/缺失值、非法输入、权限/状态差异和历史回归中选择必要用例，不要求机械穷举每类场景。
- 涉及时间、随机性、并发、重试、超时或外部服务时，必须控制不确定性并验证失败模式。
- 测试名称应描述业务行为和期望结果，避免只描述实现细节。

### 编写规范
- 默认使用 Arrange-Act-Assert（准备-执行-断言）结构，保持单个测试意图清晰。
- 测试应彼此独立，不依赖执行顺序、共享可变状态或外部环境残留。
- 测试数据应最小、明确、贴近业务语义，避免无关 fixture 淹没断言目标。
- 断言应验证可观察结果、状态变化、输出、错误或副作用，而不是内部实现步骤。

### Mock 使用边界
- 可 mock 外部不可控依赖（网络、支付、时间、随机数、第三方API），但不要 mock 被测代码本身。
- mock 必须服务于隔离不可控边界，不应用于掩盖设计问题或跳过真实业务协作。
- 当 mock 设置比测试目标更复杂时，优先改用 fake、轻量真实组件或集成测试。
## 测试反模式

- 不测试 mock 自身行为，应测试真实业务可观察结果。
- 不为了测试向生产类添加 `test-only` 方法、开关或泄露内部状态的接口。
- mock 前先理解真实依赖结构、副作用、错误模式和调用契约。
- mock 对象结构必须贴近真实对象，避免虚构字段导致假阳性。
- mock 过于复杂时，优先考虑 fake、真实轻量组件或集成测试。
- 集成测试不能作为事后补救，应在方案设计阶段规划。
- 避免只验证调用次数而不验证业务结果。
- 禁止为了覆盖率数字、假设性未来需求或未触达路径堆叠低价值测试。

## 正反例

**应触发:**
- 新增用户可观察行为、公共 API 或核心业务逻辑。
- 修复可稳定复现的 Bug，需要补回归测试。
- 重构有现成测试保护，且需要证明行为不变。

**不应触发:**
- 纯文档、模板拆分、注释或格式化调整。
- 无测试框架且本次不适合引入自动化测试。
- 一次性探索或只读诊断。

## 完成门禁

```yaml
必须检查:
  - 每个新增可观察行为都有测试，或有明确TDD-EXEMPT原因
  - RED证据记录完整: 测试名/测试命令、失败摘要、目标行为、失败原因匹配说明
  - GREEN证据记录完整: 测试命令、通过摘要、最小实现说明
  - REFACTOR后相关测试仍通过
  - VERIFY证据记录完整: 测试命令、结果摘要、剩余风险或未覆盖原因
  - 新生成的 QA schema v3 已记录 `tdd` 阶段证据，或记录 TDD-EXEMPT 与替代验证
  - 未新增不必要mock或test-only生产接口
  - 已按目标行为和风险覆盖必要的正常、错误与关键边界场景，或记录未覆盖原因
  - 测试保持独立、命名清晰、断言可观察结果
  - 无新增阻断性测试失败

表述修正:
  - 使用“新增可观察行为必须有测试”替代“每个新函数/方法必须有测试”
  - 私有helper可由覆盖其外部行为的测试保护
```
