# 需求评估规则

## 阶段A: 需求评估

### 步骤1: 检查知识库状态

```yaml
判定条件: 工作目录存在代码文件 且 需求不是"新建项目"
执行方式: 只检查与当前任务相关的既有知识；详细缺失处理见 [kb](../../kb/SKILL.md)
问题标记: 如知识库不存在/不合格，标记问题（需求分析阶段只读，不创建）
```

### 步骤2: 获取项目上下文

```yaml
执行方式: 优先复用相关知识库和会话事实，不足则定向搜索代码与测试
详细规则: 如需完整规则，读取 `kb` Skill
目的: 为评分和追问提供完整项目上下文，避免低级问题
```

### 步骤3: 需求类型判定

- 涉及产品功能且用户场景影响验收时，明确使用者、问题和成功标准；纯技术变更不附加产品分析。
- 判定需求具体类型（新项目初始化、重大功能重构、常规功能开发、技术变更等）

### 步骤4: 识别阻塞性需求缺口

<requirement_scoring>
**判断原则:**
- 先查代码和已有上下文，明确目标、预期结果、范围和实际约束。
- 用户只要求检查或提出建议时，可直接完成只读分析；不要要求其先指定未知问题。
- 改动请求存在多种会改变业务结果的解释，且无法从上下文确定时，只暂停依赖该决定的工作；可继续独立的只读调查。
- 复杂需求可用下列评分维度辅助整理，不因总分、缺少时间指标或文件数量单独阻断。是否追问取决于缺口是否改变正确性、范围或安全边界。

**追问规则:**
- 严格避免询问已知信息: 技术栈、框架、模块结构、可从代码推断的实现细节
- 只询问用户相关信息: 具体需求、业务逻辑、期望结果、优先级、约束条件
- 文档化追问: 只澄清影响实现或验收的术语歧义；稳定且值得复用的定义记录为候选，后续按 `kb` 写入收益门禁决定是否沉淀。

**评分维度(总分10分):**
- 目标明确性 (0-3分): 任务目标是否清晰具体
- 预期结果 (0-3分): 成功标准和交付物是否明确
- 边界范围 (0-2分): 任务范围和边界是否清楚
- 约束条件 (0-2分): 时间、性能、业务限制等是否说明

**处理结果:**
- 无阻塞性缺口 → 继续相关分析或已授权的实施。
- 有阻塞性缺口 → 说明缺口及影响，提出最少必要问题；不展示内部评分过程。
</requirement_scoring>

### 步骤4.2: 领域语言识别门禁

<domain_language_gate>
**触发条件（满足任一）:**
```yaml
- 用户使用项目内黑话、缩写、业务角色、状态名、流程名
- 同一概念可能存在多个叫法
- 需求依赖用户未解释的业务规则、例外规则或验收口径
- 代码/知识库中存在相关术语但当前需求用词不一致
```

**处理规则:**
- 先检查已有术语表和代码用法；无法确定且会影响当前决策时才请用户澄清相关含义或边界。
- 仅对稳定且可复用的概念记录"领域语言候选"，字段包含: 术语、定义、适用模块、来源；存在命名分歧时补充同义词/禁用叫法。
- 需求分析阶段保持只读，不直接写 `wiki/glossary.md`。
- 进入方案设计或开发实施后，由 `kb` 按写入收益门禁决定是否更新 `wiki/glossary.md`。

**不触发:**
- 通用技术术语（如 API、缓存、数据库）且项目中无特殊含义。
- 一次性描述词，不会影响命名、验收或模块边界。
</domain_language_gate>

### 步骤4.5: 大范围需求拆分门禁

<large_scope_split_gate>
**触发条件（满足任一）:**
```yaml
- 需求同时覆盖多个子系统/业务域，且不能形成单个可验证闭环
- 多个目标互相竞争，或存在需要分别确认的架构、数据和公共契约决策
```

**处理规则:**
- 文件数量和“整体/全部”等词只提示检查范围；同一机械改动或边界清晰的整体清理可作为一个闭环。
- 需要拆分时，先形成独立、可验证、可回滚的需求切片
- 每个切片必须有明确目标、范围边界、成功标准和主要风险
- 用户已授权完整范围且切片顺序不影响业务结果时，自主按依赖和风险排序，连续完成全部范围。
- 只有优先级改变业务结果、预算或授权边界时才询问；不得把未完成的已授权切片擅自降为范围外。
- 按恢复执行和审计需要选择一个包含任务分组的方案包，或为独立交付切片分别记录。
</large_scope_split_gate>

### 追问输出（存在阻塞性缺口时）

输出前设置 `PENDING_INTERACTION=REQUIREMENT_INPUT`。

使用统一输出格式，行首: `❓【HelloAGENTS】- 需求分析`

内容格式: 简要说明缺口及其影响，再提出最少必要问题；一个缺口只问一个问题，不凑固定数量。

禁止显示: 评分维度明细、分类标题、下一步建议、文件变更

**示例:**
```
❓【HelloAGENTS】- 需求分析

当前规则允许订单取消后退款，但无法确认已发货订单的业务口径，这会改变退款条件。

已发货订单是否允许直接取消并退款？
```

### 缺口后处理

```yaml
无阻塞性缺口: 继续执行阶段B；只读请求保持只读

存在阻塞性缺口:
  - 等待用户决定依赖该缺口的工作，继续不依赖答案的必要调查
  - 用户补充后只核对尚未解决的缺口，不重新执行已有有效分析
  用户选择处理:
    - "先读代码澄清" 或等价表达:
      - 仅执行只读需求澄清勘察
      - 允许读取知识库、搜索/阅读相关代码、定位模块边界、提取现有行为和约束
      - 禁止进入方案设计、禁止创建方案包、禁止修改代码或知识库
      - 勘察后核对剩余缺口；仍需业务决定时精确追问，不把代码现状当作用户确认
    - "取消":
      - 所有模式: 执行 RESET_WORKFLOW_STATE，按 output-format Skill 的 G6.2 取消格式输出
      - 取消输出示例:
        ```
        🚫【HelloAGENTS】- 已取消

        已取消: 需求分析
        ────
        🔄 下一步: 可重新描述需求或进行其他操作
        ```
  模式处理:
    - 交互确认模式: 关键缺口消除后完成阶段B，按当前授权决定后续处理
    - 推进模式: 关键缺口消除后恢复连续执行
    - 自适应授权模式: 用户已明确授权低/中风险改动时，连续进入必要的设计或开发；风险升级为高时退出并确认
```
