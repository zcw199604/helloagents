# 代码分析与输出规则

## 只读需求澄清勘察

```yaml
触发条件:
  - 用户要求现状分析，或需求缺口依赖现有代码事实

允许:
  - 读取知识库和相关代码
  - 搜索模块、接口、配置、测试和既有行为
  - 提取需求缺口对应的事实、约束和更精准追问

禁止:
  - 进入方案设计
  - 创建方案包
  - 修改代码、测试、配置或知识库
  - 将勘察结果当作用户已确认的需求

完成后:
  - 用勘察事实补齐可查证信息
  - 只读请求直接报告结果；对仍影响改动正确性的业务缺口提出必要问题
```

## 阶段B: 代码分析（按当前目标和已知边界执行）

### 步骤5: 提取关键目标、成功标准和TDD适用性

- 提取关键目标: 从完整需求中提炼核心目标
- 定义成功标准: 明确可验证的成功标准
- 提取领域语言候选: 记录术语、定义、同义词/禁用叫法、适用模块和来源，供 `kb` 同步到 `wiki/glossary.md`
- 判定TDD适用性: 强制 | 建议 | 例外 | 不确定
- 当涉及新功能、Bug修复、行为变更、核心逻辑调整或测试策略设计时，读取 `tdd` Skill
- 成功标准无法从需求和代码确定，且影响实现或验收时才追问
- 对遗留代码、无测试框架、环境不可稳定复现的场景，提前判定验证策略: 自动化测试 | 手工验证 | TDD-EXEMPT

### 步骤6: 代码分析与技术准备

```yaml
执行内容:
  - 根据模块边界、公共契约和依赖评估影响范围，不按文件数决定流程深度
  - 定位相关模块
  - 质量检查: 标记过时信息，扫描安全风险和代码异味
  - 问题诊断: 分析日志或错误信息（如有）
  - 技术信息收集（如需要）: 使用联网搜索或MCP工具(Context7)获取最新文档和最佳实践

输出物: 项目上下文信息（技术栈、模块结构、质量问题、技术约束）供方案设计阶段使用
```

## 需求分析输出

- 自适应低/中风险改动：分析结果作为内部执行上下文，连续进入必要的设计或开发，不单独输出阶段总结和评分。
- 用户只要求分析，或分析后必须等待确认：简要输出需求、成功标准、关键风险和需要用户补充的内容；不展示内部评分明细。
- `~plan`、`~auto` 等正式命令按 output-format 对应命令模板在终点统一总结，不在中间重复包装。

**需要对外总结时:**

只读分析直接回答；正式命令或需确认的复杂交付按 `output-format` 选择格式，按需填充以下信息：

1. **阶段名称:** `需求分析`
2. **阶段具体内容(≤5条要点):**
   - 📋 完整需求描述(整理)
   - 🏷️ 需求类型: 技术变更/产品功能
   - 🎯 关键目标与成功标准
   - 🧭 领域语言候选: [无/术语列表摘要，供方案设计与 kb 同步]
   - 📚 知识库状态（如要点超过5条，合并到领域语言候选或关键目标行）
3. **后续处理:**
   - 交互确认模式: 仅当后续设计超出当前授权且确需用户选择时，设置 `PENDING_INTERACTION=DESIGN_CONFIRM`；只读请求交付结论后结束
   - 自适应授权模式: 低/中风险且用户已明确授权改动时，不设置 `DESIGN_CONFIRM`，连续进入必要的设计或开发
   - 推进模式: 静默进入方案设计

## 阶段转换规则

```yaml
仍有阻塞性业务缺口: 等待该决定，继续独立的必要调查
只读请求: 输出分析结论并结束，不自动进入设计
无阻塞性缺口 且 交互确认模式: 按当前授权输出结果或等待必要确认
无阻塞性缺口 且 自适应授权模式: 完成需求分析→连续进入必要的设计或开发；风险升级为高时停止确认
无阻塞性缺口 且 (MODE_FULL_AUTH=true 或 MODE_PLANNING=true): 完成需求分析→连续进入方案设计
```
