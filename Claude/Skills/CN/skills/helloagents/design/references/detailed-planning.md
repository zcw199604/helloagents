# 详细规划规则

## 详细规划

**前提:** 用户已选择/确认方案（来自方案构思）

**重要:** 必须创建新方案包，使用当前时间戳，不得复用 `helloagents/<branch-name>/plan/` 中的遗留方案

### 动作步骤

**使用宿主精确编辑工具，保留已有工作区改动；中间步骤简要报告关键进展，不逐文件输出模板。**

**1. 创建新方案包目录**

```yaml
路径: helloagents/<branch-name>/plan/YYYYMMDDHHMM_<feature>/
冲突处理:
  1. 检查 helloagents/<branch-name>/plan/YYYYMMDDHHMM_<feature>/ 是否存在
  2. 如不存在 → 直接创建
  3. 如存在 → 使用版本后缀: helloagents/<branch-name>/plan/YYYYMMDDHHMM_<feature>_v2/
     (如 _v2 也存在，则递增为 _v3, _v4...)
示例:
  - 首次创建: helloagents/<branch-name>/plan/202511181430_login/
  - 同名冲突: helloagents/<branch-name>/plan/202511181430_login_v2/
```

**2. 新库/框架文档查询（如需要）**
```yaml
触发条件: 方案涉及项目中从未使用过的第三方库/框架，或涉及重大版本升级
执行方式: 使用联网搜索或MCP工具(Context7)查询最新文档
记录位置: how.md 的 技术方案 章节
```

**3. 生成方案文件**

读取 `templates` Skill 获取模板，生成:
- `why.md` (变更提案/产品提案)
- `how.md` (技术设计+ADR)
- `task.md` (任务清单)

**领域语言接入:**
```yaml
触发条件:
  - 需求分析输出了领域语言候选
  - 方案引入新业务概念、角色、状态、流程名或命名约定
执行:
  - 读取 `kb` Skill 的领域语言维护规则
  - 在 why.md 的核心场景中使用已确认术语
  - 在 how.md 记录待写入 `wiki/glossary.md` 的术语表变更
  - task.md 增加知识库同步任务，明确更新 `wiki/glossary.md`
约束:
  - 待确认术语不得强制用于代码命名
  - 同一概念只保留一个推荐名称，其他叫法写入同义词/禁用叫法
```

**任务清单编写规则:**
```yaml
单任务代码改动量控制:
  - 常规项目: ≤3文件/任务
  - 大型项目: ≤2文件/任务
大型项目最小改动:
  - 任务必须优先限定在直接相关模块和最小文件集合
  - 禁止把风格整理、目录搬迁、依赖升级、公共接口重命名混入功能实现
  - 如确需重构，必须拆为独立任务并说明必要性、回滚方式和验证命令
设计边界:
  - 在 how.md 明确范围内/范围外、模块职责、接口契约、数据边界和依赖边界
  - task.md 中每个代码任务必须标明执行模式、涉及文件、完成标准、验证方式和依赖关系
任务可验证性:
  - 每个任务必须能被另一个代理只读核对完成/未完成
  - 完成标准必须是布尔条件，避免"优化完成""适当调整"等不可判定描述
  - AFK 表示可自主执行；HITL 表示需要用户确认、凭据、外部环境或高风险授权
验证规模适配:
  - 常规项目优先规划覆盖核心路径、受影响契约和高风险回归的最小充分验证，不为覆盖率数字或假设性风险扩展范围
  - 大型、复杂、高故障成本或公共契约影响广的项目，可基于风险增加测试层级、覆盖范围、审查深度和验证证据；不得把有明确风险依据的全面验证简单判定为过度工程化
  - 扩大验证范围时必须在 how.md 或 task.md 记录规模/风险依据；缩减验证范围不得降低安全、公共契约和核心行为门禁
验证任务: 定期插入
安全检查: 必须包含安全检查任务
TDD任务: 对强制/建议启用TDD的可测试行为，读取 `tdd` Skill，将任务拆为 RED → GREEN → REFACTOR → VERIFY
TDD例外: 例外任务必须标注 TDD-EXEMPT 和原因
并行子代理标注:
  - 当存在可并行任务组时，读取 `hello-subagent` Skill 的触发条件
  - 在 task.md 中标注可并行组、允许写入范围、冲突域和验证命令
  - 若文件边界或依赖关系不清晰，不标注为可并行
```

**4. 风险规避措施制定**
- 基于方案构思风险评估，为实际风险制定规避措施；高风险边界按 [路由规则](../../routing/SKILL.md) 处理
- 交互确认模式或 MODE_PLANNING_INTERACTIVE=true: 询问用户
- MODE_FULL_AUTH=true 或 (MODE_PLANNING=true 且 MODE_PLANNING_INTERACTIVE=false): 规避风险
- 写入 `how.md` 的 安全与性能 章节

**4.2 ADR 候选识别**

```yaml
触发条件（满足任一）:
  - 方案选择排除了一个有实际可行性的替代方案
  - 引入或改变模块边界、数据边界、接口契约、依赖方向
  - 为降低风险选择了分阶段迁移、兼容层、适配器或回滚策略
  - 领域语言定义影响代码命名、模块边界或用户可见行为

执行:
  - 在 how.md 的 架构决策 ADR 章节写入 ADR 候选
  - 每条 ADR 至少包含: 背景、决策、替代方案、影响、状态
  - 状态使用: 候选 / 已采纳 / 已拒绝
  - 无架构或命名取舍时，明确记录"本次无 ADR 候选"
```

**4.5 方案自审门禁**

<design_self_review_gate>
**执行时机:** `why.md`、`how.md`、`task.md` 初稿生成后，输出阶段总结前

**自审清单（必须全部通过）:**
- 范围一致: `why.md` 的需求、`how.md` 的技术方案、`task.md` 的任务清单覆盖同一需求切片
- 边界清晰: 范围内/范围外、模块职责、接口契约、数据边界、依赖边界无歧义
- 最小改动: 大型项目方案优先局部修改；不存在无必要的重构、迁移、依赖升级或公共API改名
- 可验证: 每个核心场景都有对应任务和验证方式；TDD适用性已处理；验证深度与项目规模和风险相称
- 风险闭环: EHRB、安全、性能、回滚和兼容性风险已有缓解措施
- 无占位遗留: 不保留未解释的 TODO/TBD/待定/???，不留下互相矛盾的描述

**失败处理:** 修正本次发现的问题并核对受影响部分；若无法消除影响设计正确性的关键不确定性，说明缺口并等待必要决定
</design_self_review_gate>

**5. 设置方案包跟踪变量**
```yaml
设置: CREATED_PACKAGE = 步骤1创建的方案包路径
用途: 在全授权命令中传递给开发实施，确保执行正确的方案包
```

**6. 多模型审查询问（可选）**

```yaml
触发时机: 方案包文件创建完成后、输出阶段总结前
适用模式: 仅交互确认模式（询问格式见 `output-and-transition.md`）

规划命令处理:
  - 跳过询问，输出规划命令完成总结后停止
  - 在总结末尾追加提示: "💡 多模型审查: 如需审查方案包，可在规划命令完成后单独触发"

全授权命令处理:
  - 跳过询问，直接进入开发实施
  - 在最终总结末尾可提示: "💡 多模型审查: 如需复核本次实现，可单独触发只读审查"
```
