### plan/ 和 history/ 下的 task.md

**Markdown anchor链接格式按why.md实际章节标题生成**

```markdown
# 任务清单: [功能名称]

目录: `helloagents/<branch-name>/plan/YYYYMMDDHHMM_<feature>/`

---

## 并行子代理标注（可选）

启用条件: 仅当任务组独立、无顺序依赖、写入范围不重叠且验证方式明确时保留本节。

- 并行组 A: 任务 [1.1, 4.1]；允许写入: `path/to/a.ts`, `wiki/modules/a.md`；冲突域: 无；验证: `[验证命令]`
- 并行组 B: 任务 [2.1]；允许写入: `path/to/b.ts`；冲突域: 无；验证: `[验证命令]`
- 不可并行任务: [3.1, 5A.4]；原因: 安全检查/最终验证需在集成后执行

---

## 0. 方案边界确认
- [ ] 0.1 确认本次任务仅覆盖 why.md 的范围内切片，范围外内容不进入实现
- [ ] 0.2 确认 how.md 的设计边界完整，尤其是模块职责、接口契约、数据边界和依赖边界
- [ ] 0.3 大型项目确认最小改动策略: 不做无关重构、目录搬迁、依赖升级或公共API重命名

---

## 1. [核心功能模块名称]
- [ ] 1.1 在 `path/to/file.ts` 中实现 [具体功能]，验证 why.md#[需求标题anchor]-[场景标题anchor]
- [ ] 1.2 在 `path/to/file.ts` 中实现 [具体功能]，验证 why.md#[需求标题anchor]-[场景标题anchor]，依赖任务1.1

## 2. [次要功能模块名称]
- [ ] 2.1 在 `path/to/file.ts` 中实现 [具体功能]，验证 why.md#[需求标题anchor]-[场景标题anchor]，依赖任务1.2

## 3. 安全检查
- [ ] 3.1 执行安全检查（按G9: 输入验证、敏感信息处理、权限控制、EHRB风险规避）

## 4. 文档更新
- [ ] 4.1 更新 <知识库文件>

## 5. 测试

### 5A. TDD路径（适用时保留）
- [ ] 5A.1 RED: 按项目现有测试结构选择最小合适层级，为 [可观察行为] 添加失败测试，确认失败原因是 [预期原因]
- [ ] 5A.2 GREEN: 以最小生产实现让 RED 测试通过，依赖任务5A.1
- [ ] 5A.3 REFACTOR: 在测试保持通过的前提下整理实现，依赖任务5A.2
- [ ] 5A.4 VERIFY: 运行 [测试命令]，记录相关测试结果，依赖任务5A.3

### 5B. TDD-EXEMPT路径（不适用TDD时保留）
- [ ] 5B.1 TDD-EXEMPT: [例外任务]，原因: [纯文档/无行为变化/无测试框架/用户约束/其他]；替代验证: [手工验证/现有测试/代码审查/其他]
```

**任务状态符号:** 遵循 lifecycle Skill 的 G11 定义
